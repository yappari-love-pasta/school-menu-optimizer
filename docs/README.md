# qsyoku

学校給食の献立を量子アニーリング（QUBO）によって最適化するプロジェクトです。

## 概要

学校給食の献立作成において、栄養価・コスト・調理工程・レシピ相性などの多数の制約を同時に満たす組み合わせを、量子アニーリング（QUBO）で探索します。A/B 2コースの献立を同時に最適化できます。

- 参考資料: [お茶の水女子大学 卒業論文 (2023)](docs/2023grad2020509.pdf)

## 最適化方式の進化

本プロジェクトでは、課題の発見と克服を繰り返しながら3つの最適化方式を開発しました。現在のデフォルトは **方式3（並列方式）** です。

以下は、その進化の過程です。

---

### Step 1: 素朴なアプローチ — M日一括方式 (`solve_menu`)

最初のアプローチは、最も直感的な方法でした。M日分の献立を一つの巨大なQUBOとして定式化し、solverに「全部まとめて最適化してくれ」と投げる方式です。

| 項目 | 値 |
|------|-----|
| 変数数 | N × M（M=20 で 5,900） |
| solve回数 | Aコース1回 + Bコース1回 = 2回 |
| 実行時間 (M=20) | 約120秒 |

**発見された課題:**

この方式を実際に動かしてみると、2つの深刻な問題が見つかりました。

1. **スケーラビリティの壁**: M=20日で変数数が5,900に膨れ上がり、変数間の相互作用は二次的に増加します。solverが制限時間内に良い解を見つけられず、日数を増やすほど解の品質が不安定になりました。
2. **A/Bコースの不公平**: Aコースを先に解き、残ったレシピからBコースを最適化する2段階方式のため、Aが「良いレシピ」を先取りし、Bは残り物から選ばざるを得ないという構造的なバイアスがありました。

> "問題を丸ごとsolverに任せれば最適解が出るはず" — この素朴な期待は、問題サイズの現実に直面して崩れました。

---

### Step 2: 発想の転換 — 逐次方式 (`solve_menu_ab`)

方式1の課題を受けて、「大きな問題を1回解く」から「小さな問題をM回解く」へと発想を転換しました。さらに、A/Bコースを別々に解くのではなく、各日で同時に最適化することでコース間の公平性を実現しました。

| 項目 | 値 |
|------|-----|
| 変数数 | N × 2（常に590） |
| solve回数 | M回（1日1回） |
| 実行時間 (M=20) | 約70秒 |

**方式1の課題がどう解決されたか:**

1. **スケーラビリティ**: 問題サイズがN×2=590変数で固定。M=20でもM=100でも、1回のsolveの難しさは変わりません。合計時間はMに対して線形にスケールします。
2. **A/Bの公平性**: 各日 `x[N, 2]` でA/Bを同時に最適化し、`less_equal` 制約で同日のA/B重複を防止。どちらのコースも同じ条件で最適化されます。

**新たに生まれた課題:**

一方で、この方式は貪欲法（各日の決定を確定して次に進む）であるため、理論上は局所最適に陥る可能性があります。ただし、295品のレシピプールに対して使用率が約14%と余裕があり、レシピ間の品質差も小さいため、実測では品質低下は観測されませんでした。

また、「もっと速くできないか？」という次の問いが生まれました。逐次方式は1日ずつ順番に解くため、Day 1が終わるまでDay 2に着手できません。

---

### Step 3: さらなる高速化 — 並列方式 (`solve_menu_ab_speculative`) — 現在のデフォルト

逐次方式のボトルネックは「待ち時間」でした。Day 1→Day 2→...と直列に処理するため、各solveの待ち時間がそのまま積み上がります。

そこで、**前方（Day 1→）と後方（←Day M）から同時に攻める**並列方式を考案しました。前方チェーンは Amplify AE、後方チェーンは Toshiba SQBM+ と、異なるsolverを使い分けることで、APIの待ち時間を重ね合わせます。

| 項目 | 値 |
|------|-----|
| 変数数 | N × 2（常に590） |
| solve回数 | M回（前方・後方で分担） |
| 実行時間 (M=20) | 約55秒 |

**方式2からの改善点:**

- 前方・後方の2プロセスが同時にsolveを実行するため、実行時間を約21%短縮
- 2つの異なるsolverを使うことで、解の多様性が向上
- 前方・後方から攻めるため、逐次方式の「後半にレシピが偏る」傾向を緩和

**トレードオフ:**

- Amplify AE と Toshiba SQBM+ の2つのAPIトークンが必要
- 前方・後方チェーンの合流地点（中央日）で整合性を取る追加処理が必要

---

### 進化のまとめ

| 方式 | 変数数 | 実行時間 (M=20) | 短縮率 | 解決した課題 |
|------|--------|-----------------|--------|-------------|
| Step 1: M日一括 | 5,900 | ~120秒 | — | — |
| Step 2: 逐次 | 590 | ~70秒 | 42%短縮 | スケーラビリティ、A/B公平性 |
| Step 3: 並列 | 590 | ~55秒 | 54%短縮 | 直列処理の待ち時間 |

各方式は前の方式の課題を発見し、それを克服する形で進化しています。最終的に、解の品質を維持しながら実行時間を半分以下に短縮することができました。

### スケーラビリティ: レシピ数が増えたらどうなるか？

現在のレシピ数は約300ですが、一般的な給食システムでは300〜500品のレシピを扱います。レシピ数 N が増加した場合に、各方式がどのようにスケールするかを示します。

#### 変数数の比較 (M=20)

| レシピ数 (N) | Step 1: M日一括 (N×M) | Step 2/3: 逐次・並列 (N×2) | 変数数の差 |
|-------------|----------------------|---------------------------|-----------|
| 300 | 6,000 | 600 | 10倍 |
| 350 | 7,000 | 700 | 10倍 |
| 400 | 8,000 | 800 | 10倍 |
| 450 | 9,000 | 900 | 10倍 |
| 500 | 10,000 | 1,000 | 10倍 |

#### QUBO行列サイズの比較 (M=20)

QUBOの計算量は変数数の **二乗** に比例します。変数間の相互作用項（QUBO行列の非ゼロ要素数）がsolverの探索空間を決定するため、変数数の差はそのまま二乗で効いてきます。

| レシピ数 (N) | Step 1: 相互作用項 | Step 2/3: 相互作用項 | 計算量の差 |
|-------------|-------------------|---------------------|-----------|
| 300 | ~36,000,000 | ~360,000 | **100倍** |
| 400 | ~64,000,000 | ~640,000 | **100倍** |
| 500 | ~100,000,000 | ~1,000,000 | **100倍** |

Step 1（M日一括）ではレシピ数が増えるほどQUBO行列が爆発的に大きくなり、solverの制限時間内に良い解を見つけることが困難になります。一方、Step 2/3では変数数が常に N×2 に抑えられるため、N=500でも1,000変数に収まり、現実的な時間で安定して解を得られます。

#### 実行時間の見込み (M=20)

| レシピ数 (N) | Step 1: M日一括 | Step 2: 逐次 | Step 3: 並列 |
|-------------|----------------|-------------|-------------|
| 300 (現在) | ~120秒 | ~70秒 | ~55秒 |
| 400 | 実用困難 (推定200秒超) | ~80秒 | ~65秒 |
| 500 | 実用困難 (推定300秒超) | ~90秒 | ~70秒 |

Step 2/3は1回のsolveあたりの変数数が増えるため若干の時間増加はありますが、線形的な増加に留まります。Step 1はQUBO行列の二次的増大により、N=400以上では実用的な時間内での解の取得が困難になると推定されます。

## データ

- `data/reciept.json` — レシピ情報
- `data/reciept-cost.json` — レシピとそれぞれのコスト

## 技術スタック

- 言語: Python
- ライブラリ: [Amplify SDK v1](https://amplify.fixstars.com/ja/docs/amplify/v1/index.html), Flask, NumPy

## セットアップ

### 1. 依存パッケージのインストール

```bash
pip install amplify flask numpy python-dotenv
```

### 2. 環境変数の設定

`.env.example` をコピーして `.env` ファイルを作成し、各solverのトークンを設定します。

```bash
cp .env.example .env
```

```
AMPLIFY_TOKEN=your_amplify_token_here
TOSHIBA_SQBM_TOKEN=your_toshiba_sqbm_token_here
PORT=8080
```

- `AMPLIFY_TOKEN`: [Amplify](https://amplify.fixstars.com/ja/) から取得
- `TOSHIBA_SQBM_TOKEN`: [Toshiba SQBM+](https://annealing-cloud.com/) から取得（並列方式を使う場合に必要）

## 起動方法

```bash
python main.py
```

Flask サーバーが `http://localhost:8080` で起動します。

## 検証手順

サーバー起動後、以下の curl コマンドで献立最適化 API を呼び出せます。

```bash
curl -X POST http://localhost:8080/optimize \
  -H "Content-Type: application/json" \
  -d '{"M": 3, "cost": 900}'
```

### リクエストパラメータ

| パラメータ | 型 | 説明 | デフォルト |
|---|---|---|---|
| `M` | int | 献立を生成する日数 | 5 |
| `cost` | float | M日分の合計コスト目標値 | 1500.0 |
